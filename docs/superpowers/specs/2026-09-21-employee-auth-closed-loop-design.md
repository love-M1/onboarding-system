# 员工账号认证与入职任务闭环设计

## 1. 目标

为现有新员工入职任务协同系统增加真实账号认证，形成以下闭环：
密码登
1. HR 使用手机号（工号）和录系统。
2. HR 录入新同事的基本信息并完成建档。
3. 系统在同一事务中根据任务模板生成该员工的全部入职任务。
4. 新员工使用 HR 建档时登记的手机号获取验证码并完成注册。
5. 注册账号自动绑定对应的员工档案。
6. 新员工登录后只看到自己的任务清单，并逐项确认完成。
7. HR 可在进度汇总和档案详情中查看实时完成情况。

该流程替代当前“选择角色后直接进入系统”的演示登录，同时移除前端可自行伪造角色和部门的信任方式。

## 2. 范围

### 2.1 本次实现

- 手机号验证码申请与校验。
- 员工自助注册，并绑定 HR 已创建的员工档案。
- 手机号和密码登录。
- 基于 Bearer Token 的会话认证、会话恢复和注销。
- HR、员工两类前端主要工作台。
- 员工只能查看和确认自己的任务。
- HR 账号由启动配置初始化。
- MySQL 初始化脚本、H2 测试脚本、接口测试和项目文档同步更新。

### 2.2 非目标

- 不接入真实短信供应商。演示环境通过接口返回并显示验证码，生产环境可关闭该行为。
- 不实现找回密码、修改密码、修改手机号和多设备会话管理。
- 不开放 HR 自助注册。HR 属于高权限角色，必须由部署配置初始化或后续由管理员管理。
- 不重构任务模板、统计和归档业务本身。

## 3. 角色与账号规则

### 3.1 HR

- 通过启动配置初始化一个 HR 账号。
- 默认演示账号由配置项提供，数据库已存在时不会覆盖密码。
- 可创建员工档案、维护模板、查看统计和归档。
- 不允许代替员工确认个人入职任务。

### 3.2 EMPLOYEE

- 只能通过公开注册流程创建。
- 注册手机号必须匹配一条未归档的员工档案。
- 账号的姓名、部门和 `empId` 从员工档案自动读取，注册表单不允许修改。
- 只能查看和确认自己的任务。

### 3.3 DEPARTMENT

- 保留现有后端角色和权限判断，供历史数据和后续管理员维护使用。
- 本次不提供部门责任人自助注册入口。
- 原有按责任部门查看和确认任务的接口行为保持兼容。

## 4. 账号与员工档案约束

- 手机号是登录账号，统一称为“手机号（工号）”。
- 手机号格式为 `1[3-9]` 开头的 11 位中国大陆手机号。
- 创建员工档案时手机号必填，且不能与其他档案重复。
- 已归档员工不能注册账号。
- 一个员工档案最多绑定一个账号，一个手机号最多对应一个账号。
- 密码长度为 8 至 32 位，至少包含字母和数字。
- 密码只保存 BCrypt 哈希。

## 5. 完整操作流程

### 5.1 HR 建档

1. HR 登录后进入“入职档案”。
2. 填写新员工姓名、手机号、部门、岗位和入职时间。
3. 后端校验手机号必填、格式正确且唯一。
4. 后端写入员工档案。
5. 后端读取全部任务模板，在同一事务中批量写入 `emp_task`。
6. 前端提示“建档成功，已生成 N 项入职任务”。

### 5.2 员工注册

1. 员工在登录页切换到“注册”。
2. 输入 HR 建档时使用的手机号。
3. 前端调用验证码接口，后端确认员工档案存在且未归档。
4. 后端生成 6 位验证码，5 分钟有效，60 秒内禁止重复发送。
5. 演示环境返回验证码，前端显示并允许用户继续。
6. 员工输入验证码、密码和确认密码。
7. 后端校验验证码、密码规则、手机号唯一性及档案状态。
8. 后端创建 `EMPLOYEE` 账号，并绑定员工档案。
9. 注册成功后自动登录，进入“我的任务”。

### 5.3 员工登录

1. 员工输入手机号和密码。
2. 后端校验账号状态和 BCrypt 密码。
3. 后端签发随机 Bearer Token，保存 Token 的 SHA-256 哈希和 8 小时有效期。
4. 前端保存 Token 和用户摘要。
5. 前端按角色进入 HR 工作台或员工任务页。

### 5.4 员工确认任务

1. 员工打开“我的任务”。
2. 后端只返回账号绑定的 `empId` 对应任务。
3. 任务仍按应完成日期排序，并显示待完成、已完成、已逾期状态。
4. 到达入职日期且档案未归档时，“确认完成”可用。
5. 后端再次校验任务归属，成功后将任务改为已完成并记录完成时间。
6. HR 刷新档案详情或进度汇总后可看到最新状态。

## 6. 后端设计

### 6.1 数据表

#### user_account

- `accountId`：主键。
- `phone`：唯一登录账号。
- `passwordHash`：BCrypt 哈希。
- `role`：`HR`、`EMPLOYEE` 或 `DEPARTMENT`。
- `empId`：员工账号绑定档案，非员工账号为空。
- `displayName`：显示名称。
- `department`：账号所属部门。
- `status`：`ACTIVE` 或 `DISABLED`。
- `createTime`、`updateTime`。
- `empId` 建立到员工档案的外键，删除员工档案时同步删除对应账号。

#### phone_verification

- `verificationId`：主键。
- `phone`：验证手机号。
- `code`：6 位验证码。
- `expiresAt`：过期时间。
- `usedAt`：使用时间。
- `attemptCount`：校验失败次数。
- `createTime`：发送时间。

#### auth_session

- `sessionId`：主键。
- `tokenHash`：Bearer Token 的 SHA-256 哈希，唯一。
- `accountId`：关联账号。
- `expiresAt`：过期时间。
- `createTime`、`lastAccessTime`。
- `accountId` 建立到账号的外键，删除账号时同步删除会话。

### 6.2 认证接口

所有接口保持现有 `ApiResponse` 包装格式。

#### POST `/api/auth/verification-codes`

请求：

```json
{
  "phone": "13800000001"
}
```

响应：

```json
{
  "expiresIn": 300,
  "resendAfter": 60,
  "devCode": "123456"
}
```

`devCode` 仅在 `AUTH_EXPOSE_CODE` 为真时返回。生产环境为假时，该字段为空。手机号已经注册时拒绝发送验证码。

#### POST `/api/auth/register`

请求：

```json
{
  "phone": "13800000001",
  "code": "123456",
  "password": "Onboard123"
}
```

响应：

```json
{
  "token": "opaque-token",
  "expiresAt": "2026-09-21 22:00:00",
  "user": {
    "accountId": 2,
    "phone": "13800000001",
    "displayName": "张三",
    "role": "EMPLOYEE",
    "empId": 10,
    "department": "研发部"
  }
}
```

#### POST `/api/auth/login`

请求：

```json
{
  "phone": "13800000001",
  "password": "Onboard123"
}
```

响应结构与注册一致。

#### GET `/api/auth/me`

根据 Bearer Token 返回当前用户摘要，用于前端刷新页面后恢复登录状态。

#### POST `/api/auth/logout`

删除当前会话。接口保持幂等，重复注销不报错。

### 6.3 认证拦截

- 仅 `/api/auth/verification-codes`、`/api/auth/register` 和 `/api/auth/login` 为公开接口。
- `/api/auth/me` 和 `/api/auth/logout` 必须携带有效的 Bearer Token。
- 其他 `/api/**` 接口必须携带 `Authorization: Bearer <token>`。
- 拦截器根据 Token 哈希查询有效且未过期的会话。
- 有效会话写入 `AuthContext`，其中包含账号、角色、员工编号和部门。
- 缺失、无效或过期 Token 返回未认证错误，前端清理状态并跳转登录页。
- `X-Role`、`X-Department` 和 `X-Operator` 不再参与真实授权。

### 6.4 任务权限

- HR：可查看所有任务，不可确认任务。
- EMPLOYEE：查询时后端强制使用账号绑定的 `empId`；确认时校验任务归属。
- DEPARTMENT：保持历史行为，只能查看和确认本部门任务。

## 7. 前端设计

### 7.1 登录与注册页

- 使用“登录 / 注册”分段切换。
- 登录表单仅包含手机号（工号）和密码。
- 注册表单包含手机号、验证码、密码和确认密码。
- 验证码按钮显示 60 秒倒计时。
- 演示环境收到 `devCode` 后直接回填验证码并给出提示。
- 登录或注册成功后按真实角色进入对应页面。
- 页面不再提供 HR/部门角色选择。

### 7.2 登录状态

Pinia 保存以下状态：

- `token`
- `accountId`
- `phone`
- `displayName`
- `role`
- `empId`
- `department`

Axios 请求拦截器自动添加 Bearer Token。收到未认证响应时清理本地状态并跳转登录页。

### 7.3 工作台

- HR：保留任务模板、入职档案、进度汇总和归档管理。
- EMPLOYEE：只显示“我的任务”菜单和员工任务页。
- 员工任务页不显示员工筛选、责任部门筛选和分页外的人工身份信息。
- 确认任务前继续使用二次确认，成功后刷新列表。
- 台账中可显示员工姓名、任务名称、应完成日期和状态；员工页面不展示无权限的操作。

## 8. 错误处理

新增统一业务错误码，至少覆盖：

- 手机号格式错误。
- 员工档案不存在或尚未建档。
- 员工档案已归档。
- 手机号已注册。
- 验证码不存在、已过期、已使用或错误次数过多。
- 验证码发送过于频繁。
- 密码格式不符合要求。
- 手机号或密码错误。
- 登录会话缺失、无效或已过期。

错误信息应直接指导下一步操作，例如：

- “请先由 HR 完成员工建档”
- “验证码已过期，请重新获取”
- “该手机号已注册，请直接登录”

## 9. 测试设计

### 9.1 后端自动化测试

- HR 初始化账号可以登录。
- 未认证请求不能访问员工和任务接口。
- HR 创建员工后，手机号可申请验证码。
- 未建档手机号不能申请验证码。
- 错误验证码不能注册。
- 正确验证码可以注册并返回员工身份。
- 重复手机号不能注册。
- 错误密码不能登录。
- 正确密码可以登录并访问受保护接口。
- 员工只能查询自己的任务。
- 员工不能确认其他员工的任务。
- 员工可以在满足日期条件时确认自己的任务。
- 注销后原 Token 失效。
- 旧 `X-Role` 请求头不再获得权限。

### 9.2 前端验证

- 登录、注册、验证码倒计时和错误提示可用。
- 刷新页面后可通过 `me` 接口恢复会话。
- HR 与员工登录后看到不同导航。
- 员工任务页只显示自己的任务，确认完成后状态及时刷新。
- `npm run build` 成功。

### 9.3 端到端验收

1. 使用 HR 手机号和密码登录。
2. 创建一名新员工，确认生成模板对应数量的任务。
3. 退出 HR 账号。
4. 使用新员工手机号申请验证码。
5. 完成注册并自动进入“我的任务”。
6. 确认只看到该员工自己的任务。
7. 完成一项任务，确认状态和完成时间更新。
8. 重新登录 HR，在档案详情和进度汇总中看到完成结果。

## 10. 部署与兼容

- MySQL 初始化脚本新增三张认证表，并清理认证表的执行顺序先于员工表。
- H2 测试脚本保持与 MySQL 结构兼容。
- 后端启动时确保 HR 初始化账号存在。
- 默认演示参数通过配置暴露，部署时必须使用环境变量覆盖默认密码。
- 演示验证码返回由 `AUTH_EXPOSE_CODE` 控制，默认便于课程演示开启，生产环境必须关闭。
- README 和启动说明更新登录方式、演示账号、验证码行为和认证接口。

## 11. 验收标准

- HR 建档后自动生成任务。
- 新员工可以使用建档手机号完成注册并绑定档案。
- 员工可以登录、查看自己的任务并逐项确认完成。
- 未登录请求不能访问业务接口。
- 员工无法查看或修改其他员工的任务。
- HR 能看到任务完成后的最新状态。
- 密码不以明文保存，登录后使用不可伪造的 Bearer Token。
- 后端测试和前端构建通过。
